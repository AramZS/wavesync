# Requirements Document

## Introduction

WaveSync is a working Spotify visualizer built with Vue 2, vue-router (history mode), and Vuex, with a canvas-based real-time visualizer. It currently depends on an Express server (`server/`) that handles Spotify OAuth using the server-side Authorization Code flow (with a client secret) and serves the built static assets in production.

This feature re-architects WaveSync into a fully static, serverless single-page application deployed on Netlify. The Spotify OAuth flow migrates from the server-side Authorization Code flow to the **Authorization Code with PKCE** flow, which runs entirely in the browser with no client secret and no backend. This allows the Express server to be removed entirely, simplifying deployment and scaling.

The scope covers: the browser-only PKCE authorization flow, browser-side token lifecycle management (acquisition, storage, refresh, expiry handling), error handling for authentication and playback states, Netlify deployment configuration (SPA fallback routing, build settings, build-time environment variables), and complete removal of all server infrastructure and its dependencies. The behavior of the visualizer, the real-time sync loop, and rendering must be preserved after the migration.

## Glossary

- **WaveSync_App**: The static single-page Vue application that runs entirely in the browser and contains all client-side logic for authentication, token management, playback synchronization, and visualization.
- **Auth_Module**: The browser-side component of WaveSync_App responsible for executing the Authorization Code with PKCE flow, including generating PKCE parameters, constructing the authorization URL, handling the redirect callback, and exchanging authorization codes for tokens.
- **Token_Manager**: The browser-side component of WaveSync_App responsible for storing, reading, refreshing, and clearing Spotify tokens.
- **Sync_Engine**: The browser-side component (currently `src/wavesync/sync.js`) that polls the Spotify Web API for the currently playing track, fetches track analysis and features, and drives the real-time synchronization loop.
- **Visualizer**: The canvas-based rendering system that renders visuals driven by the Sync_Engine.
- **PKCE**: Proof Key for Code Exchange (RFC 7636), an OAuth 2.0 extension that secures the Authorization Code flow for public clients using a code verifier and code challenge instead of a client secret.
- **Code_Verifier**: A cryptographically random string generated by the Auth_Module, used in the PKCE flow and sent during the token exchange.
- **Code_Challenge**: A value derived from the Code_Verifier using the S256 (SHA-256) transformation, sent in the authorization request.
- **State_Parameter**: A random value generated by the Auth_Module and included in the authorization request to protect against cross-site request forgery; validated when the callback is received.
- **Access_Token**: The short-lived Spotify OAuth token used to authorize Spotify Web API requests.
- **Refresh_Token**: The Spotify OAuth token used to obtain a new Access_Token when the current Access_Token expires.
- **Spotify_Token_Endpoint**: The Spotify token endpoint at `https://accounts.spotify.com/api/token`.
- **Spotify_Authorize_Endpoint**: The Spotify authorization endpoint at `https://accounts.spotify.com/authorize`.
- **Redirect_URI**: The URI registered in the Spotify Developer Dashboard where Spotify redirects the browser after authorization. Configured for the deployed Netlify site and for the local development host.
- **Client_ID**: The public Spotify application identifier, provided to WaveSync_App as a build-time environment variable.
- **Playback_Scope**: The Spotify OAuth scope `user-read-playback-state`.
- **Netlify**: The static hosting platform targeted for deployment.
- **SPA_Fallback**: A hosting rewrite rule that serves `/index.html` with HTTP status 200 for all routes so client-side routing and deep links work without a server.
- **Build_Time_Config**: Configuration values injected at build time via `VUE_APP_`-prefixed environment variables.

## Requirements

### Requirement 1: Generate PKCE Authorization Parameters

**User Story:** As a user, I want the application to securely begin Spotify authorization in my browser, so that I can log in without any backend server or client secret.

#### Acceptance Criteria

1. WHEN a user activates the login control on the home page, THE Auth_Module SHALL generate a Code_Verifier that is a random string between 43 and 128 characters using the unreserved character set defined by RFC 7636.
2. WHEN a Code_Verifier is generated, THE Auth_Module SHALL derive a Code_Challenge from the Code_Verifier using the S256 transformation.
3. WHEN a user activates the login control on the home page, THE Auth_Module SHALL generate a State_Parameter as a random string between 16 and 128 characters.
4. WHEN the Code_Verifier and State_Parameter are generated, THE Auth_Module SHALL persist the Code_Verifier and the State_Parameter in browser session storage such that both values remain retrievable after the redirect to the Spotify_Authorize_Endpoint and back.
5. THE Auth_Module SHALL use the Web Crypto API to produce random values for the Code_Verifier and the State_Parameter.
6. IF the Web Crypto API is unavailable, THEN THE Auth_Module SHALL abort the authorization flow, SHALL NOT redirect to the Spotify_Authorize_Endpoint, and SHALL display an error message indicating that secure authorization cannot be started.
7. IF persisting the Code_Verifier or the State_Parameter to browser session storage fails, THEN THE Auth_Module SHALL abort the authorization flow, SHALL NOT redirect to the Spotify_Authorize_Endpoint, and SHALL display an error message indicating that authorization could not be started.

### Requirement 2: Redirect to Spotify Authorization

**User Story:** As a user, I want to be sent to Spotify to grant access, so that WaveSync can read my playback state.

#### Acceptance Criteria

1. WHEN the Code_Challenge and State_Parameter are prepared, THE Auth_Module SHALL construct an authorization URL targeting the Spotify_Authorize_Endpoint with URL-encoded query parameters `response_type=code`, `client_id` set to the Client_ID, `redirect_uri` set to the Redirect_URI, `scope` set to the Playback_Scope, `code_challenge_method=S256`, `code_challenge` set to the Code_Challenge, and `state` set to the State_Parameter.
2. WHEN the authorization URL is constructed and the login transition animation completes, THE Auth_Module SHALL navigate the browser to the authorization URL within 500 milliseconds of the animation completing.
3. THE Auth_Module SHALL request the Playback_Scope and no additional scopes.
4. IF the Code_Challenge or State_Parameter is absent or empty when authorization is initiated, THEN THE Auth_Module SHALL abort construction of the authorization URL, SHALL NOT navigate the browser, and SHALL display an error indication that authorization could not be started.

### Requirement 3: Handle the Authorization Callback

**User Story:** As a user, I want WaveSync to complete login when Spotify redirects me back, so that I reach the visualizer in an authenticated state.

#### Acceptance Criteria

1. WHEN the browser loads the Redirect_URI route with a `code` query parameter and a `state` query parameter, THE Auth_Module SHALL read the returned State_Parameter and the persisted State_Parameter.
2. IF the Redirect_URI route is loaded without a required `code` or `state` query parameter and without an `error` parameter, THEN THE Auth_Module SHALL abort the token exchange, remove the persisted Code_Verifier and State_Parameter, display an authentication error, and navigate the browser to the home route.
3. IF the returned State_Parameter does not match the persisted State_Parameter, THEN THE Auth_Module SHALL abort the token exchange, remove the persisted Code_Verifier and State_Parameter, display an authentication error, and navigate the browser to the home route.
4. WHEN the returned State_Parameter matches the persisted State_Parameter, THE Auth_Module SHALL exchange the authorization code for tokens by sending a POST request to the Spotify_Token_Endpoint with `grant_type=authorization_code`, `code` set to the returned authorization code, `redirect_uri` set to the Redirect_URI, `client_id` set to the Client_ID, and `code_verifier` set to the persisted Code_Verifier.
5. THE Auth_Module SHALL send the token exchange request without a client secret.
6. WHEN the token exchange returns a successful response containing an Access_Token and a Refresh_Token, THE Token_Manager SHALL store the returned Access_Token and Refresh_Token.
7. WHEN the tokens are stored after a successful token exchange, THE Auth_Module SHALL remove the persisted Code_Verifier and the persisted State_Parameter from browser storage.
8. WHEN the tokens are stored after a successful token exchange, THE WaveSync_App SHALL navigate the browser to the `/visualizer` route.
9. IF the token exchange request does not complete within 30 seconds or returns an unsuccessful response or a response missing the Access_Token, THEN THE Auth_Module SHALL remove the persisted Code_Verifier and State_Parameter, display an authentication error, and navigate the browser to the home route.
10. IF the browser loads the Redirect_URI route with an `error` query parameter, THEN THE Auth_Module SHALL remove the persisted Code_Verifier and State_Parameter, display an authentication error, and navigate the browser to the home route.

### Requirement 4: Browser-Side Token Storage

**User Story:** As a user, I want my Spotify session handled safely in my browser, so that my tokens are not exposed longer than necessary.

#### Acceptance Criteria

1. THE Token_Manager SHALL store the Access_Token and the Refresh_Token exclusively in `sessionStorage` or in in-memory application state, and SHALL NOT write either token to a cookie.
2. WHEN the browser tab or session that holds the tokens is closed, THE Token_Manager SHALL ensure the stored Access_Token and Refresh_Token are discarded and no longer retrievable within that browser context.
3. WHEN the Sync_Engine requires authorization for a Spotify Web API request, THE Token_Manager SHALL provide the currently stored Access_Token.
4. IF the Sync_Engine requires authorization and no Access_Token is currently stored, THEN THE Token_Manager SHALL withhold any Access_Token and return an indication that authorization is unavailable, leaving stored token state unchanged.
5. WHEN a new Access_Token is obtained from a token response, THE Token_Manager SHALL replace the previously stored Access_Token with the new Access_Token.
6. WHERE a token response includes a new Refresh_Token, THE Token_Manager SHALL replace the previously stored Refresh_Token with the new Refresh_Token.
7. IF a token response does not contain a valid Access_Token, THEN THE Token_Manager SHALL retain the previously stored Access_Token and Refresh_Token unchanged and return an indication that the token operation failed.

### Requirement 5: Browser-Side Token Refresh

**User Story:** As a user, I want WaveSync to keep my session alive while I listen, so that the visualizer continues without forcing me to log in again.

#### Acceptance Criteria

1. WHEN a Spotify Web API request returns HTTP status 401, THE Sync_Engine SHALL request a new Access_Token from the Token_Manager before issuing any further playback polling request.
2. WHEN a new Access_Token is required and a Refresh_Token is stored, THE Token_Manager SHALL send a POST request to the Spotify_Token_Endpoint with `grant_type=refresh_token`, `refresh_token` set to the stored Refresh_Token, and `client_id` set to the Client_ID.
3. THE Token_Manager SHALL send the refresh request without a client secret.
4. WHEN the refresh request returns an HTTP 2xx response containing a non-empty Access_Token, THE Token_Manager SHALL store the returned Access_Token.
5. WHEN the Token_Manager has stored a refreshed Access_Token, THE Sync_Engine SHALL resume playback polling using the new Access_Token on the next scheduled polling interval.
6. IF a new Access_Token is required and no Refresh_Token is stored, THEN THE WaveSync_App SHALL navigate the browser to the home route.
7. IF the refresh request returns a non-2xx response or a 2xx response without a non-empty Access_Token, THEN THE WaveSync_App SHALL navigate the browser to the home route.
8. IF the refresh request does not complete within 10 seconds, THEN THE WaveSync_App SHALL navigate the browser to the home route.

### Requirement 6: Preserve Playback Synchronization Behavior

**User Story:** As a user, I want the visualizer to behave exactly as before the migration, so that my experience is unchanged.

#### Acceptance Criteria

1. THE Sync_Engine SHALL request the currently playing track from the Spotify Web API endpoint `https://api.spotify.com/v1/me/player` using the current Access_Token.
2. WHEN the currently playing response indicates a track that differs from the currently synced track, or when no track has yet been synced, THE Sync_Engine SHALL request track analysis from `https://api.spotify.com/v1/audio-analysis/{id}` and track features from `https://api.spotify.com/v1/audio-features/{id}` for the returned track.
3. WHILE a track is actively playing, THE Sync_Engine SHALL drive the real-time synchronization loop and the Visualizer SHALL render visuals synchronized to the track.
4. IF the currently playing response indicates no active playback, THEN THE Sync_Engine SHALL set the no-playback state and continue polling at the 2500 millisecond ping delay.
5. IF a Spotify Web API request returns HTTP status 401, THEN THE Sync_Engine SHALL trigger the Token_Manager refresh flow before resuming polling.
6. WHEN the home page is displayed, THE Visualizer SHALL render the static demo intervals it rendered before the migration, driven by the fixed-mode static interval generator.

### Requirement 7: Netlify SPA Fallback Routing

**User Story:** As a user, I want to open the visualizer and the OAuth redirect route directly, so that deep links and the login callback work without a server.

#### Acceptance Criteria

1. THE WaveSync_App SHALL include a Netlify SPA_Fallback configuration that rewrites every request path not matching an existing static asset to `/index.html` with HTTP status 200.
2. THE WaveSync_App SHALL retain vue-router in history mode.
3. WHEN a user requests the `/visualizer` route directly, THE SPA_Fallback SHALL serve `/index.html` with HTTP status 200 so the WaveSync_App renders the visualizer route.
4. WHEN Spotify redirects the browser to the Redirect_URI route, THE SPA_Fallback SHALL serve `/index.html` with HTTP status 200 so the Auth_Module handles the callback.
5. IF a requested path matches an existing static asset under the published output directory, THEN THE SPA_Fallback SHALL serve that asset with HTTP status 200 without rewriting to `/index.html`.
6. WHEN the SPA_Fallback serves `/index.html` for a deep-link route, THE SPA_Fallback SHALL preserve the original request path, query string, and fragment so the WaveSync_App resolves the intended route and the Auth_Module receives the callback parameters.

### Requirement 8: Netlify Build Configuration

**User Story:** As a developer, I want Netlify to build and publish WaveSync correctly, so that deployments are reproducible.

#### Acceptance Criteria

1. THE WaveSync_App SHALL declare, in a Netlify configuration committed to the repository, a build command verbatim of `npm run build`.
2. THE WaveSync_App SHALL declare, in a Netlify configuration committed to the repository, a publish directory verbatim of `dist`.
3. WHEN `npm run build` runs successfully, THE WaveSync_App SHALL produce an entry `index.html` and compiled asset bundles in the `dist` directory using the Vue CLI build.
4. IF the Vue CLI build fails, THEN THE `npm run build` script SHALL exit with a non-zero status code and SHALL NOT produce a publishable `dist` directory.

### Requirement 9: Build-Time Client Configuration

**User Story:** As a developer, I want Spotify configuration supplied at build time, so that no secrets are embedded in source and the app targets the correct environment.

#### Acceptance Criteria

1. THE WaveSync_App SHALL read the Client_ID from a `VUE_APP_`-prefixed build-time environment variable.
2. THE WaveSync_App SHALL read the Redirect_URI from a `VUE_APP_`-prefixed build-time environment variable.
3. THE WaveSync_App SHALL exclude any client secret from the source code, the build output, and the configuration.
4. THE WaveSync_App SHALL replace the former `PROJECT_ROOT` environment variable usage with the Build_Time_Config values.
5. WHERE WaveSync_App runs in local development, THE Redirect_URI SHALL be set to the local development host `http://localhost:8080/callback`.
6. IF the Client_ID build-time environment variable or the Redirect_URI build-time environment variable is absent or an empty string at build time, THEN THE WaveSync_App build SHALL fail and SHALL emit an error indicating which required Build_Time_Config value is missing.

### Requirement 10: Remove Server Infrastructure

**User Story:** As a developer, I want the Express server and its dependencies removed, so that the project is fully static and simpler to maintain.

#### Acceptance Criteria

1. THE WaveSync_App SHALL remove the `server` directory, including the Express entry point and the `auth`, `login`, `callback`, and `refresh` routes.
2. THE WaveSync_App SHALL remove the server-only dependencies `express`, `cookie-parser`, `compression`, `express-history-api-fallback`, `request`, and `dotenv` from the project dependencies.
3. THE WaveSync_App SHALL remove the `start` npm script and remove the server portion of the `serve` npm script.
4. THE WaveSync_App SHALL provide a `serve` npm script that runs the Vue CLI development server (`vue-cli-service serve`) without starting any Node server process.
5. THE WaveSync_App SHALL remove browser-side reading and writing of the `SPOTIFY_ACCESS_TOKEN`, `SPOTIFY_REFRESH_TOKEN`, `SPOTIFY_REFRESH_CODE`, and `SPOTIFY_AUTH_ID` cookies previously set by the server.
6. WHEN the server infrastructure has been removed, THE `npm run build` and `npm run lint` scripts SHALL complete successfully and the WaveSync_App SHALL run without any Node server process.

### Requirement 11: Update Documentation for Serverless Netlify Setup

**User Story:** As a developer, I want the README to describe the serverless Netlify setup, so that I can deploy WaveSync correctly.

#### Acceptance Criteria

1. THE README SHALL contain two distinct Redirect URI entries for the Spotify Developer Dashboard: one for the deployed Netlify domain and one for the local development host, each shown as a copyable value.
2. THE README SHALL state the Netlify build command verbatim as `npm run build` and the Netlify publish directory verbatim as `dist`.
3. THE README SHALL list, by name, both `VUE_APP_`-prefixed environment variables (the Client ID variable and the Redirect URI variable) to be set in the Netlify UI, each identified as a required value.
4. IF the README contains any reference to a client secret (for example a `CLIENT_SECRET` value) or to the removed Express server (for example `npm run start` or a server-side callback route), THEN the requirement SHALL be considered unmet; the README SHALL contain zero such references.

### Requirement 12: Verify Dependencies Are Declared Before Use

**User Story:** As a developer, I want every npm package the project uses to be declared in `package.json` before it is used, so that builds are reproducible, dependencies are not silently relying on hoisted or transitive installs, and supply-chain risks from undeclared packages are avoided.

#### Acceptance Criteria

1. BEFORE the WaveSync_App source code, build scripts, test files, or tooling configuration import or invoke an npm package, THE package SHALL be present as a named entry in the `dependencies` or `devDependencies` of `package.json`.
2. IF an npm package is used by the WaveSync_App but is not present in `package.json`, THEN the requirement SHALL be considered unmet and the package SHALL be added to the appropriate `dependencies` or `devDependencies` section before use.
3. THE WaveSync_App SHALL declare each npm package in the section matching its usage, placing packages required only for development, testing, or build tooling in `devDependencies` and packages required at application runtime in `dependencies`.
4. WHEN a package name is added to `package.json`, THE declared package name SHALL exactly match the intended official package name so that typosquatting or wrapper packages are not introduced.
